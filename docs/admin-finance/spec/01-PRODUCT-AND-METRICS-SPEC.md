# Техническое задание: административная финансовая аналитика Atlas System

**Версия:** 1.1 draft
**Дата:** 05.08.2026
**Статус:** для согласования бизнеса, аналитика и разработки
**Интерфейс:** внутренняя административная панель Atlas System
**Часовой пояс отчётности:** UTC

---

## 1. Цель системы

Создать внутренний административный дашборд, который позволяет руководству Atlas System:

- контролировать входящие и исходящие денежные потоки;
- понимать, в какие циклы пользователи направляют средства;
- видеть фактически выплаченную Delta, возврат основной суммы и партнёрские выплаты;
- контролировать Platform Fee и доход головного аккаунта;
- отслеживать ликвидность и будущие обязательства;
- контролировать статус головного аккаунта и риск потери партнёрского дохода;
- сопоставлять трафик сайта, подключения кошельков и создание циклов;
- анализировать рекламные кампании и источники трафика;
- раскрывать каждую агрегированную сумму до транзакций и событий, из которых она рассчитана.

Дашборд является управленческой аналитикой. Он не должен подменять бухгалтерскую или налоговую отчётность.

## 2. Пользователи и права доступа

### 2.1. Роли

| Роль | Доступ |
| --- | --- |
| Owner / CEO | Все показатели, адреса, транзакции, экспорт, формулы и настройки уведомлений |
| Finance Admin | Все финансовые показатели, сверка и экспорт; без управления ролями |
| Analyst | Просмотр агрегатов и обезличенных детализаций; адреса кошельков маскируются |
| Marketing | GA4, кампании, воронка, циклы и доход по источникам; без treasury-деталей |
| Auditor | Только чтение, транзакции и журнал расчётов/изменений |

### 2.2. Требования безопасности

- Авторизация обязательна для всех маршрутов административной панели.
- Доступ к данным проверяется сервером, а не только скрытием элементов интерфейса.
- Полные адреса кошельков по умолчанию маскируются: `0x1234…ABCD`.
- Просмотр полного адреса, экспорт и изменение формул записываются в audit log.
- Секреты провайдеров, приватные ключи и seed-фразы не должны попадать во frontend, логи или аналитическую БД.

## 3. Термины и единицы измерения

| Термин | Определение |
| --- | --- |
| Principal / Support Amount | Основная сумма, фактически направленная пользователем в Smart Cycle |
| Incoming Flow | Сумма подтверждённого Principal, поступившего при создании циклов |
| Principal Returned | Основная сумма, фактически выплаченная пользователю при закрытии/claim цикла |
| Gross Delta | Delta до удержания Platform Fee и других предусмотренных удержаний |
| Platform Fee from Delta | Часть Gross Delta, удержанная в пользу платформы; не является расходом сверх Gross Delta |
| Net Delta Received | Delta, фактически полученная участником после удержаний |
| Partner Reward at Creation | Отдельное партнёрское вознаграждение, возникающее и выплачиваемое при создании цикла |
| Partner Reward streamed | Отдельное партнёрское вознаграждение, возникающее и выплачиваемое при claim |
| Gross Partner Reward | Отдельный вид расхода сверх Delta до удержания Platform Fee |
| Platform Fee from Partner Reward | Часть Gross Partner Reward, удержанная в пользу платформы; не прибавляется сверх Gross Partner Reward |
| Net Partner Reward | Сумма, фактически полученная партнёром после удержания Platform Fee |
| Participant & Partner Payouts | Principal Returned + Net Delta Received + Net Partner Rewards at Creation + Net Partner Rewards at Claim |
| Net Flow | Incoming Flow − Outgoing Flow за одинаковый период |
| Accounting Liquidity | Накопленный Incoming Flow − накопленный Outgoing Flow с начала учёта до выбранной даты |
| LP Market Value | Рыночная стоимость позиции пула ликвидности; отдельный показатель, не равный Accounting Liquidity |
| Head Account Income | Фактически полученная головным аккаунтом статусная разница и другие подтверждённые партнёрские выплаты |
| Company Revenue | Platform Fee + Head Account Income до вычета расходов и налогов |
| Company Revenue Rate | Company Revenue / Incoming Flow × 100% |
| Connected Wallet | Уникальный нормализованный адрес, для которого сервер подтвердил успешное подключение/авторизацию |
| Wallet Without Cycle | Connected Wallet без подтверждённого события создания цикла |
| Zero-balance Wallet | Кошелёк с нулевым балансом выбранного токена; показывается отдельно от Wallet Without Cycle |
| As-of Block | Последний блок сети, включённый в расчёт |

Все денежные значения по умолчанию отображаются в USDT. Для каждого значения хранится точность исходного токена; округление выполняется только в интерфейсе.

- 7 календарных дней;

- период;

## 6. Входящий поток

### 6.1. Incoming Flow Total

**Определение:** сумма Principal по успешно подтверждённым событиям создания циклов в выбранном периоде.

```text
Incoming Flow = SUM(cycle_created.principal_amount)
```

В расчёт включаются только события:

- с подтверждённой транзакцией;
- с успешным receipt;
- с допустимым контрактом и токеном;
- не признанные дубликатами или отменёнными событиями.

### 6.2. Разбивка по циклам

Для каждого цикла показывать:

- системный `cycle_type_id`;
- публичное название;
- тип: Lockup / Daily;
- тариф или диапазон Principal;
- количество открытых циклов;
- количество уникальных кошельков;
- общий Incoming Flow;
- средний и медианный размер Principal;
- долю цикла от общего Incoming Flow;
- изменение доли относительно прошлого периода.

```text
Cycle Inflow Share = Cycle Incoming Flow / Total Incoming Flow × 100%
```

Сумма долей всех строк после округления должна составлять приблизительно 100%. Внутренний расчёт выполняется без округления.

### 6.3. Дополнительные показатели входящего потока

- количество новых участников, впервые создавших цикл;
- количество повторных участников;
- среднее число циклов на активный кошелёк;
- Top-10 кошельков по Incoming Flow;
- концентрация: доля Top-10 кошельков в общем потоке;
- доля крупнейшего цикла;
- доля крупнейшей партнёрской ветки, если связь разрешена бизнес-логикой.

## 7. Исходящий поток

### 7.0. Утверждённый payout waterfall

Владелец продукта подтвердил следующие правила:

1. Партнёрское вознаграждение выплачивается в два момента: при создании цикла и при claim.
2. Партнёрское вознаграждение является отдельным видом расхода и выплачивается сверху к Delta.
3. Platform Fee удерживается из соответствующей Gross-суммы и не является дополнительным расходом сверх неё.

```text
Gross Delta = Net Delta to User + Platform Fee from Delta + Other Delta Deductions

Gross Partner Reward at Creation =
  Net Partner Reward at Creation
  + Platform Fee from Partner Reward at Creation
  + Other Partner Deductions

Gross Partner Reward streamed =
  Net Partner Reward streamed
  + Platform Fee from Partner Reward streamed
  + Other Partner Deductions
```

Партнёрские вознаграждения не входят в Gross Delta. Они учитываются отдельными расходными компонентами.

### 7.1. Outgoing Flow Total

```text
Participant & Partner Payouts = Principal Returned
                               + Net Delta Received
                               + Net Partner Reward at Creation
                               + Net Partner Reward streamed
```

В Outgoing Flow включаются только фактически исполненные выплаты. Начисленные, но ещё не выплаченные суммы отображаются в прогнозе обязательств и не смешиваются с фактом.

### 7.2. Обязательная разбивка

| Компонент | Что показывать |
| --- | --- |
| Principal Returned | Сумма, количество закрытых циклов, уникальные получатели |
| Gross Delta | Delta до удержания комиссии |
| Platform Fee from Delta | Комиссия платформы с фактически выплаченной Delta |
| Net Delta Received | Сумма, поступившая участникам после удержания |
| Gross Partner Reward at Creation | Отдельный расход, возникший при создании цикла |
| Net Partner Reward at Creation | Фактически поступившая партнёрам сумма после удержания Fee |
| Gross Partner Reward streamed | Отдельный расход, возникший при claim |
| Net Partner Reward streamed | Фактически поступившая партнёрам сумма после удержания Fee |
| Platform Fee from Partner Rewards | Удержанная часть двух видов Gross Partner Reward |

### 7.3. Разбивка закрытых циклов

Для каждого типа цикла:

- количество закрытых циклов;
- количество уникальных получателей;
- Principal Returned;
- Gross Delta;
- Net Delta Received;
- Gross/Net Partner Reward streamed;
- доля данного цикла в Outgoing Flow;
- средняя выплата на один закрытый цикл;
- среднее время от открытия до выплаты;
- доля успешных claim относительно доступных к claim.

### 7.4. Доля партнёрских выплат

Необходимо показывать три разных коэффициента, поскольку они отвечают на разные управленческие вопросы:

```text
Partner Reward / Incoming = Total Net Partner Rewards / Incoming Flow × 100%
Partner Reward / Payouts = Total Net Partner Rewards / Participant & Partner Payouts × 100%
Partner Reward / Cycle Cohort Principal = Cohort Gross Partner Rewards / Cohort Principal × 100%
```

Основной управленческий маркер из исходного запроса: `Partner Reward / Incoming`.

## 8. Platform Fee

### 8.1. Принцип признания

Platform Fee признаётся только по факту выплаты, из Gross-суммы которой комиссия реально удержана в пользу платформы. Будущая комиссия с начисленной, но не полученной пользователем Delta или Partner Reward в текущий доход не включается. Platform Fee показывается отдельным распределением Gross, но не прибавляется к Gross повторно.

### 8.2. Формулы

```text
Platform Fee from Delta = SUM(actual_fee_transfers linked to delta payout)
Platform Fee from Partner = SUM(actual_fee_allocations linked to partner payouts at creation and claim)
Platform Fee Total = Platform Fee from Delta + Platform Fee from Partner
```

Для контроля также рассчитывать:

```text
Effective Delta Fee Rate = Platform Fee from Delta / Gross Delta Paid × 100%
Effective Partner Fee Rate = Platform Fee from Partner / Gross Partner Rewards × 100%
```

Ожидаемая ставка задаётся версионной конфигурацией контракта. Нельзя жёстко прописывать 10% во frontend.

### 8.3. Детализация

Каждая строка Platform Fee должна раскрываться до:

- типа комиссии;
- связанной выплаты;
- адреса плательщика/получателя;
- цикла;
- gross amount;
- fee amount;
- effective rate;
- transaction hash;
- block number и UTC timestamp;
- версии правил/контракта.

## 9. Доход компании

### 9.1. Company Revenue

```text
Company Revenue = Platform Fee Total + Head Account Income
```

`Head Account Income` включает только фактически полученную головным аккаунтом статусную разницу и подтверждённые партнёрские выплаты, относящиеся к компании.

```text
Company Revenue Rate = Company Revenue / Incoming Flow × 100%
```

Показывать:

- Platform Fee Total;
- Head Account Income;
- Company Revenue;
- Company Revenue Rate;
- Company Revenue Target и денежное значение цели за тот же период;
- gap в процентных пунктах и денежный surplus/shortfall к цели;
- визуальный bridge `Incoming Flow → Platform Fee + Head Account → Company Revenue`;
- изменение к прошлому периоду;
- накопительный график;
- распределение по циклам, веткам и источникам трафика.

Текущий управленческий ориентир Company Revenue Rate равен `4%`. Контроль
считает только суммы одного UTC-периода и обязан явно отличать same-period cash
indicator от cohort take rate. При нулевом Incoming Flow процент выводится как
`N/A`; отрицательные суммы на frontend нормализовывать нельзя в production,
они должны отклоняться контрактом источника.

### 9.1.1. Доля Atlas в партнёрских выплатах

Отдельно от Platform Fee и общего Company Revenue рассчитывается эффективность
головного аккаунта Atlas в партнёрской программе:

```text
Partner Capture Rate =
  Confirmed Atlas Head Account Referral Receipts
  / Confirmed Gross Partner Rewards Paid To Network
  × 100%

Partner Capture Gap = Actual Partner Capture Rate − Approved Target
```

Текущий управленческий target равен `35%`: из каждых `$100` фактически
выплаченных Partner Rewards сетью Atlas стремится получать `$35` на головной
аккаунт. Это цель, а не обещание или фиксированная доходность.

Обязательные правила расчёта:

- numerator включает только Head Account receipts по реферальной программе;
- Platform Fee, собственные переводы и другие доходы компании исключаются;
- denominator включает Gross Partner Reward при создании и при claim;
- обе стороны берутся за один UTC-период и по одному finality cut;
- начисленные, но не выплаченные суммы показываются отдельно и не входят в rate;
- каждый receipt связан с payout/event и reconciliation status;
- интерфейс показывает actual rate, target 35%, gap в п.п., суммы numerator и
  denominator, разложение creation/streamed и временной график.

Операционная policy для MVP:

- `healthy`: `rate >= 35%`;
- `warning`: `33% <= rate < 35%`;
- `critical`: `rate < 33%`;
- сигнал и его recovery подтверждаются двумя последовательными
  finalized-срезами, чтобы не реагировать на один неполный bucket;
- shortfall = `max(0, Gross Partner Rewards Paid × 35% − Atlas Referral Income)`;
- shortfall — диагностическое денежное отклонение, а не рекомендация
  вносить средства;
- перед управленческим действием проверяются attribution, reconciliation,
  ruleset, статусы и compression прямых веток.

Risk Center содержит только локальный what-if контроль до подключения
production alert engine. Пресеты 32%, 34% и 35% показывают critical,
warning и healthy соответственно. Изменение сценария:

- не изменяет DEMO-факт или approved target;
- не создаёт production alert, платёж или funding instruction;
- показывает только будущий severity, shortfall и порядок проверки.

На Head Account локально настраиваются три типа будущих сигналов:
warning, critical и recovered. Production-настройка потребует server-side
RBAC, MFA, audit log и версионный ruleset.

Partner Capture alert lifecycle:

1. Первый finalized-срез ниже 35% переводит контроль в `pending`, но не
   создаёт alert.
2. Второй последовательный срез ниже цели открывает `warning`; два
   среза ниже 33% открывают `critical`.
3. Acknowledgement фиксирует owner/timestamp, но не закрывает source condition.
4. Первый finalized-срез от 35% переводит сигнал в `recovering`.
5. Второй здоровый срез закрывает сигнал как `recovered`.
6. Переходы opened/escalated/downgraded/acknowledged/recovered хранятся
   append-only; изменение ruleset не переписывает историю.

В LOCAL DEMO журнал хранится только в browser localStorage. Он не является
tamper-evident audit log и не переносится между браузерами.

Активный Partner Capture alert включается в общую очередь Risk Center наравне
с другими сигналами. Очередь фильтруется по severity, состоянию,
ответственному и SLA-категории. Acknowledgement обычных UI-only сигналов
сохраняется после reload только в текущем браузере; неизвестные и устаревшие
ID отбрасываются. Подтверждение Partner Capture делегируется его lifecycle
journal, чтобы единая очередь и профильный журнал не расходились по статусу.
Production-реализация обязана хранить owner, SLA, acknowledgement actor/time и
историю переходов на сервере в append-only audit trail.

### 9.2. Ограничение терминологии

Company Revenue нельзя называть чистой прибылью. Для расчёта Net Profit требуется отдельный контур расходов:

- инфраструктура;
- маркетинг;
- персонал;
- юридические и операционные расходы;
- налоги;
- компенсации и корректировки.

### 9.3. Управленческий план роста

План роста хранится отдельно от финансового факта и не участвует в ledger,
reconciliation или расчёте чистой прибыли.

```text
Monthly Flow Target = Approved Previous Month Actual × (1 + Growth Rate)
Target Pace To Date = Monthly Flow Target × Elapsed Calendar Days / Days In Month
Remaining Flow = max(0, Monthly Flow Target − Current Month Actual)
Required Daily Pace = Remaining Flow / Remaining Calendar Days
Projected Month End = Current Month Actual / Elapsed Days × Days In Month
Planned Company Revenue = Monthly Flow Target × Approved Planning Take Rate
```

Для текущего управленческого сценария `Growth Rate = 40%`. Planning take rate
из предоставленной таблицы равен `4%`, но это отдельное утверждаемое допущение,
а не фактический Company Revenue Rate.

Экран обязан показывать:

- утверждённую базу прошлого месяца и её источник;
- цель текущего/следующего месяца;
- факт на текущую дату;
- линейный target pace, отклонение и прогноз конца месяца;
- сумму, которую нужно добрать, и средний требуемый поток на оставшиеся дни;
- versioned сценарий по месяцам, автора, дату утверждения и историю изменений;
- явный статус `PLAN`, отдельно от `ACTUAL`, `FORECAST` и `RECONCILED`.

Система контролирует суммарный дневной/месячный поток. Она не требует, чтобы
каждая отдельная транзакция была больше предыдущей: после каждого подтверждённого
поступления пересчитывается остаток и необходимый средний темп.

Предоставленный годовой сценарий содержит округлённые суммы и 30-дневные
ориентиры, поэтому визуальный шаг между соседними строками может отличаться от
40%. Каноническая production-цель всегда рассчитывается от точного
неокруглённого факта прошлого месяца.

## 10. Ликвидность и обязательства

### 10.1. Accounting Liquidity

```text
Accounting Liquidity at Date D =
  Cumulative Incoming Flow through D
  − Cumulative Outgoing Flow through D
  + Approved Manual Adjustments
```

Ручные корректировки допустимы только как отдельные записи с основанием, автором и audit log. Исходные события не редактируются.

### 10.2. График ликвидности

- календарь выбора даты;
- остаток на начало дня;
- Incoming Flow за день;
- Outgoing Flow за день;
- остаток на конец дня;
- дневное изменение;
- минимальное и максимальное значение за период;
- отметки дней с отрицательным Net Flow или аномальным снижением.

### 10.3. LP Market Value

LP Market Value показывается отдельным графиком и отдельной карточкой. Не допускается суммирование или подмена Accounting Liquidity рыночной стоимостью LP.

Для LP отображать:

- текущую стоимость позиции;
- состав токенов;
- цену оценки и источник;
- uncollected fees;
- диапазон позиции и in-range/out-of-range;
- время последнего обновления.

### 10.4. Будущие обязательства

Необходимо добавить отдельный контур **Forecast Outgoing / Прогноз выплат**. Он пересчитывается при каждом новом цикле, закрытии, claim, изменении правил или изменении доступной ликвидности.

Прогноз строится только на основе существующих подтверждённых циклов. Гипотетические будущие циклы пользователей не входят в обязательства и могут учитываться только отдельным сценарием ожидаемого Incoming Flow.

Для каждого будущего временного интервала показывать:

- количество циклов, достигающих maturity/claim-eligibility;
- Scheduled Principal — Principal существующих циклов, который может потребоваться вернуть;
- Projected Gross Delta — расчётная Delta до удержаний;
- Projected Platform Fee from Delta;
- Projected Net Delta to Users;
- Projected Gross Partner Reward streamed — отдельный будущий расход сверх Delta;
- Projected Platform Fee from Partner Reward streamed;
- Projected Net Partner Reward streamed;
- Pending/Failed Gross Partner Reward at Creation — только неисполненные выплаты, которые должны были произойти при создании цикла;
- Total Gross Contract Outflow — все отдельные переводы, которые должен выполнить контракт;
- прогнозируемый остаток ликвидности;
- требуемый дополнительный приток/пополнение;
- уровень уверенности прогноза.

### 10.5. Горизонты прогноза

Обязательные быстрые периоды:

- остаток текущего дня;
- следующие 24 часа;
- завтра;
- следующие 7 дней;
- следующая календарная неделя;
- следующие 30 дней;
- следующий календарный месяц;
- следующие 90 дней;
- произвольный диапазон в пределах 90 дней.

Максимальный рабочий горизонт первой версии — 90 дней. Периоды 6 месяцев и год для прогноза не требуются, поскольку новые циклы существенно изменят картину и создадут ложную точность.

Гранулярность:

- до 48 часов — час или день;
- до 31 дня — день;
- 32–90 дней — день с возможностью агрегации по неделям.

### 10.6. Формулы будущих выплат

```text
Scheduled Principal(t) =
  Σ Principal активных циклов,
  достигающих claim-eligibility в интервале t

Projected Gross Delta(t) =
  Σ Delta, рассчитанная по версии правил каждого цикла

Projected Net Delta(t) =
  Projected Gross Delta(t)
  − Projected Platform Fee from Delta(t)
  − Projected Other Delta Deductions(t)

Projected Gross Partner Reward streamed(t) =
  Σ Partner Reward streamed,
  рассчитанный по версии правил каждого цикла

Projected Net Partner Reward streamed(t) =
  Projected Gross Partner Reward streamed(t)
  − Projected Platform Fee from Partner Reward streamed(t)
  − Projected Other Partner Deductions at Claim(t)
```

Партнёрское вознаграждение при создании цикла относится к фактическому Outgoing периода создания. В будущий forecast оно попадает только при статусе `pending` или `failed`, если обязательство ещё не исполнено.

Ключевая формула требуемой gross-суммы:

```text
Total Gross Contract Outflow(t) =
  Scheduled Principal(t)
  + Projected Gross Delta(t)
  + Projected Gross Partner Reward streamed(t)
  + Pending/Failed Gross Partner Reward at Creation(t)
```

Platform Fee уже входит в соответствующие Gross Delta и Gross Partner Reward и не прибавляется к потребности повторно. Partner Reward является отдельным расходом сверх Delta, поэтому Gross Partner Reward streamed прибавляется отдельно. Backend рассчитывает итог по фактическому графу transfer-операций и версии правил контракта, а не суммирует карточки frontend.

### 10.7. Требуемый внешний приток

Главный операционный показатель:

```text
Projected Balance_s(t) =
  Projected Balance_s(t−1)
  + Confirmed Inflow_s(t)
  − Total Gross Contract Outflow_s(t)

Required Additional Liquidity_s(t) = MAX(
  0,
  Required Reserve_s(t) − Projected Balance_s(t)
)

Peak Funding Gap_s(H) =
  MAX over t in H of Required Additional Liquidity_s(t)
```

Расчёт выполняется последовательно по каждому временному bucket. Это исключает ошибку, когда один и тот же текущий баланс используется для покрытия каждого будущего дня. Ожидаемый, но ещё не подтверждённый Incoming Flow нельзя считать гарантированным источником покрытия; он показывается только в сценариях.

Дополнительно рассчитывать:

```text
Forecast Coverage Ratio(t) =
  Available Contract Liquidity(now) /
  Total Gross Contract Outflow(t)

Forecast Liquidity After Payouts(t) =
  Projected Balance(t)
```

Если обязательства равны нулю, Coverage Ratio отображается как `N/A`.

### 10.8. Три сценария

| Сценарий | Расчёт |
| --- | --- |
| Committed | Только известный Principal и уже детерминированные отдельные выплаты |
| Base | Committed + расчётная Delta + партнёрские выплаты по действующим правилам |
| Stress | Base + safety buffer и консервативные допущения по задержке/отсутствию нового Incoming Flow |

Нельзя называть Base или Stress гарантированным долгом, если выплата зависит от claim пользователя, ликвидности, активности системы или других условий Smart Cycle.

### 10.9. Динамический пересчёт

Forecast snapshot пересчитывается при событиях:

- `cycle_created` — добавляет будущую нагрузку в дату maturity;
- `cycle_closed` или `claim_paid` — удаляет исполненную нагрузку;
- изменение статуса claim;
- изменение версии правил Delta/partner rewards;
- новый входящий перевод;
- изменение ликвидности контракта;
- reorg или reconciliation correction.

Целевая задержка пересчёта после нового подтверждённого цикла — не более 5 минут. В интерфейсе показывать `calculated_at`, `as_of_block` и возраст прогноза.

Пример: если сегодня создан однодневный цикл на 100 USDT, после подтверждения транзакции завтрашний bucket автоматически увеличивается на Principal и рассчитанные связанные выплаты по версии правил этого цикла.

### 10.10. Экран прогноза

В блоке «Прогноз выплат» отображать:

1. KPI: к выплате за 24 часа.
2. KPI: к выплате за 7 дней.
3. KPI: Required Additional Liquidity.
4. KPI: минимальный Forecast Coverage Ratio.
5. Stacked bar chart по времени: Principal / Net Delta / Partner Rewards / Platform Fee.
6. Линию прогнозируемого остатка ликвидности.
7. Линию safety threshold.
8. Переключатель Committed / Base / Stress.
9. Таблицу будущих bucket с количеством циклов и составом выплат.
10. Drill-down до каждого активного цикла и формулы его расчёта.

На главном Overview добавить компактную карточку «Ближайшие выплаты» с горизонтами `24 ч`, `7 дней`, `30 дней`, суммой к выплате и дефицитом покрытия.

### 10.11. Точность и backtesting

После наступления даты forecast bucket система сохраняет план и сравнивает его с фактом:

```text
Forecast Error = Actual Outgoing − Forecast Outgoing
Forecast Error % = ABS(Actual − Forecast) / Actual × 100%
```

Отдельно измерять ошибку по Principal, Delta и партнёрским выплатам. Это необходимо для настройки Base/Stress-сценариев и safety buffer.

Исторические forecast snapshots не перезаписываются после наступления даты. Новый расчёт создаёт новую версию snapshot.

```text
Liquidity Coverage Ratio = Available Accounting Liquidity /
                           Forecast Outgoing for selected horizon
```

Операционные горизонты контроля ликвидности: 24 часа, 7 дней, 30 дней и 90 дней.

## 11. Net Flow

```text
Net Flow = Incoming Flow − Outgoing Flow
Net Flow Margin = Net Flow / Incoming Flow × 100%
```

Показывать:

- за выбранный период;
- накопительным итогом;
- по дням/неделям/месяцам;
- по циклам;
- по источникам трафика;
- положительные и отрицательные периоды;
- сравнение с прошлым аналогичным периодом.

Если Incoming Flow равен нулю, процентный показатель выводится как `N/A`, а не как 0%.

### 12.4. Участники и лидеры

Административный модуль должен позволять найти участника по:

- полному адресу кошелька;
- нормализованной реферальной ссылке или реферальному коду;
- внутреннему Atlas ID.
- точному неизменяемому номеру личной ветки головного аккаунта.

Номер личной ветки (`headAccountBranchOrdinal`) является отдельным устойчивым
идентификатором связи с головным аккаунтом, а не номером строки, текущей
позицией сортировки или глобальным публичным ID. Он назначается монотонно,
уникален в пределах головного аккаунта, после назначения не меняется и не
используется повторно. При исправлении referral attribution прежний номер
переходит в `retired`, но не выдаётся другому участнику. Поиск по номеру всегда
точный; номер не обходит row-level authorization и не раскрывает полный wallet.

Поиск должен учитывать все действующие и исторические версии контрактов. Частичный адрес кошелька допускается только как подсказка среди уже разрешённых администратору записей; неоднозначный результат нельзя открывать автоматически.

Карточка участника содержит:

- маскированный и полный адрес с контролируемым раскрытием;
- Atlas ID, реферальный код, sponsor/upline и дату входа;
- текущий партнёрский статус и историю статусов;
- первую линию: количество кошельков, количество кошельков с циклами, Principal, активные и завершённые циклы, выплаты;
- всю структуру: количество участников, глубину, Principal, циклы и выплаты;
- личные и структурные циклы с версиями правил;
- фактически полученные Delta и Partner Reward отдельно;
- Partner Reward at Creation и Partner Reward streamed отдельно;
- будущие обязательства, относимые к структуре участника;
- последнюю on-chain и кабинетную активность;
- ссылки на подтверждающие транзакции и исходные события.

Для первой линии обязательна таблица с drill-down в карточку каждого участника. Доступны сортировка и фильтры по Principal, статусу, количеству циклов, выплатам, дате последней активности и признаку риска.

### 12.5. Средства компании и KPI лидера

Администратор с отдельным разрешением может зарегистрировать факт предоставления лидеру средств компании. Запись не создаёт on-chain перевод и не заменяет финансовый ledger; она связывается с подтверждающей транзакцией или утверждённым внутренним документом.

Хранить:

- сумму и токен;
- дату предоставления;
- tx hash или ссылку на подтверждающий документ;
- ответственного сотрудника;
- назначение и срок;
- согласованные KPI;
- статус: `planned`, `active`, `completed`, `overdue`, `cancelled`;
- комментарий к закрытию.

KPI настраиваются версионно и могут включать:

- объём первой линии;
- объём всей структуры;
- количество новых кошельков с первым подтверждённым циклом;
- количество активных участников первой линии;
- retention активных участников;
- срок выполнения;
- фактически полученный компанией доход, относимый к структуре.

Для каждого KPI показывать target, actual, процент выполнения, срок, тренд и прогноз выполнения. Изменение target после запуска плана сохраняет предыдущую версию и основание изменения.

### 12.6. Административные заметки

Заметки являются приватными административными данными и не отображаются участнику. Для каждой заметки хранить автора, время, текст, категорию, напоминание и историю изменений.

Требования безопасности:

- отдельное разрешение `leader_management` на просмотр и изменение;
- отдельное разрешение на раскрытие полного адреса и финансовых документов;
- все просмотры полного адреса, создание, редактирование и удаление заметок записываются в audit log;
- обычный редактор не удаляет историю заметки физически;
- запрещено хранить seed phrase, private key, пароль, 2FA-код и другие секреты;
- экспорт заметок и корпоративного финансирования доступен только явно разрешённой роли;
- поиск и карточка используют только данные Atlas и подтверждённые публичные on-chain события, без скрытого профилирования человека за пределами системы.

## 13. Головной аккаунт компании

### 13.1. Текущий статус

Показывать:

- адрес головного аккаунта в маскированном виде;
- текущий партнёрский статус;
- ставка/уровень статуса;
- дата и блок последнего изменения;
- активные условия, благодаря которым статус сохраняется;
- срок завершения личного цикла;
- объём первой линии;
- объём структуры;
- сколько осталось до следующего статуса по каждому условию.

### 13.2. Доход головного аккаунта

- фактически полученная статусная разница;
- прочие подтверждённые партнёрские выплаты;
- количество выплат;
- средняя выплата;
- доля Head Account Income от всех партнёрских выплат сети;
- доля Head Account Income от Incoming Flow;
- распределение по первой линии и веткам.

Для каждого лично приглашённого участника головного аккаунта вести отдельную
строку ветки:

- `headAccountBranchOrdinal`, Atlas ID и маскированный wallet;
- статус и ставка ветки на выбранном `asOfBlock`;
- статус и ставка головного аккаунта на том же block/ruleset cut;
- `compressionGapBps = max(headRateBps - branchRateBps, 0)`;
- состояние `earning`, `near`, `matched`, `surpassed`, `inactive`, `unknown`;
- фактически полученный доход по ветке отдельно at Creation и at Claim;
- дату и блок последнего изменения ставки;
- evidence до partner accrual и подтверждённого transfer.

Пример: ставка головного аккаунта 60%, ставка ветки 44%, разрыв равен 16
процентным пунктам. Разрыв не умножается интерфейсом на весь Principal ветки.
Денежное начисление рассчитывает только versioned Partner ruleset на своей
разрешённой payout base и округляет в установленном порядке. UI показывает
этот расчёт отдельно от фактически поступивших переводов.

При `compressionGapBps = 0` новые дифференциальные начисления по ветке
показываются как остановленные, но исторический доход не обнуляется. Любое
решение должно подтверждаться Partner API и независимым расчётом на одном
ruleset/as-of block.

### 13.3. Собственные средства компании в первой линии

Показывать только кошельки, помеченные в защищённом реестре как принадлежащие компании:

- Principal в активных циклах;
- количество активных циклов;
- ближайшие даты завершения;
- полученная Delta;
- полученные партнёрские выплаты;
- фактическая доходность без гарантированных прогнозных формулировок.

Средства компании, пользовательские средства и ликвидность платформы не должны смешиваться в одном показателе.

## 14. Уведомления и контроль рисков

### 14.1. Обязательные уведомления

- завершение личного цикла головного аккаунта через 72, 48 и 24 часа;
- риск потери статуса из-за снижения объёма первой линии;
- достижение следующего статуса;
- отрицательный Net Flow выше заданного порога;
- снижение Accounting Liquidity;
- Liquidity Coverage Ratio ниже порога;
- аномальное изменение Partner Reward / Incoming;
- отклонение effective Platform Fee rate от конфигурации;
- сокращение compression gap конкретной ветки до установленного порога;
- переход ветки в `matched`/`surpassed`, когда дифференциальное начисление
  становится нулевым;
- восстановление положительного разрыва после изменения статусов.

Compression-уведомление содержит номер ветки, старую и новую ставки, старый и
новый gap, ruleset version, as-of block и ссылку на участника. Дедупликация
выполняется по branch + transition + ruleset + block; повторный polling не
создаёт новый сигнал. Уведомление не предлагает финансовое действие и не меняет
статус, правила или on-chain состояние.
- расхождение contract events и USDT transfers;
- задержка индексатора или GA4;
- отсутствие данных по критическому источнику;
- концентрация потока в одном кошельке/цикле/ветке выше порога.

### 14.2. Каналы

- центр уведомлений в админке;
- email;
- Telegram-уведомления в административный чат при отдельной настройке.

Каждое уведомление имеет severity, статус, время создания, подтверждение просмотра и ссылку на первичные данные.

## 16. Проверка расчётов кампании 1–7 августа

До программирования расчётного блока владелец продукта должен подтвердить:

1. Для Lockup 30: `3.4 × 7 = 23.8`, а не ровно 24. Нужно правило округления.
2. Для Daily 200 / $100 / Executive указана сумма `$72`, но разбивка `$3.6 сразу + $14.4 постепенно` даёт `$18`.
3. Для Daily 200 / тарифа $10,000 нужно определить, почему расчёт на каждые $100 отличается от обычного Daily 200 / $100.
4. Нужно указать, являются ли суммы планом, начислением или фактической выплатой.
5. Требуется формальная версия партнёрских правил, действовавшая в период кампании.

Пока эти пункты не согласованы, расчёты помечаются `requires_review` и не используются в финансовом итоге.

## 20. Сверка и качество данных

### 20.1. Reconciliation

Для каждого финансового показателя выполняется сверка:

1. Событие контракта найдено.
2. Транзакция успешна.
3. Фактический token transfer соответствует событию.
4. Суммы частей сходятся с gross amount.
5. Событие не является дубликатом.
6. Блок входит в выбранный as-of checkpoint.

Расхождения не удаляются, а попадают в очередь `reconciliation exceptions`.

### 20.2. Свежесть

- on-chain/ledger: целевая задержка не более 5 минут;
- GA4: показывать фактическую задержку источника, допустима более высокая задержка;
- LP prices: показывать время последней цены;
- при превышении SLA карточка помечается `stale`;
- частичные данные запрещено выдавать как полный итог без явной метки.

### 20.3. Версионность формул

Каждая агрегированная запись содержит `formula_version`. Изменение формулы не перезаписывает старые отчёты без контролируемого пересчёта.

## 24. Критерии приёмки

1. Сумма Incoming Flow совпадает с подтверждёнными cycle-created transfers на тестовом диапазоне.
2. Outgoing Flow раскладывается на Principal, Net Delta и Net Partner Rewards без остатка.
3. Gross amount = net amount + связанная Platform Fee + прочие удержания для каждой выплаты, где они предусмотрены.
4. Platform Fee признаётся одновременно с фактической связанной выплатой: при создании цикла для Partner Reward at Creation и при claim для Delta и Partner Reward streamed.
5. Сумма циклов и их долей соответствует Incoming Flow выбранного периода.
6. Net Flow равен Incoming − Outgoing для каждой точки и итогового периода.
7. Accounting Liquidity на дату воспроизводится из event ledger и корректировок.
8. LP Market Value не смешивается с Accounting Liquidity.
9. Connected Wallet, Wallet Without Cycle и Zero-balance Wallet считаются отдельными сегментами.
10. Статус головного аккаунта и остаток до следующего статуса совпадают с действующими правилами контракта.
11. Уведомления 72/48/24 часа проходят тест с контролируемым временем.
12. Любой KPI раскрывается до транзакций и source events.
13. Ошибка одного источника отображается как ошибка/частичные данные и не превращает сумму в ноль.
14. Экспорт воспроизводит фильтры, формулу, as-of block и итог экрана.
15. Ролевой доступ и audit log проходят отдельные тесты.
16. Desktop, tablet и mobile не содержат наложений или обрезанного текста.
17. Новый подтверждённый цикл появляется в правильном forecast bucket не позднее чем через 5 минут.
18. Однодневный цикл, созданный сегодня, увеличивает прогноз завтрашнего дня на сумму, рассчитанную по его версии правил.
19. Исполненный claim удаляется из будущих обязательств и попадает в фактический Outgoing Flow без двойного учёта.
20. Platform Fee не прибавляется сверх соответствующей Gross-суммы; обе партнёрские выплаты учитываются как отдельные расходы сверх Delta.
21. Required Additional Liquidity равен нулю при достаточном покрытии и показывает дефицит при недостаточном покрытии.
22. Committed, Base и Stress дают воспроизводимые результаты на одном as-of block.
23. Прогноз не включает гипотетический будущий Incoming Flow как гарантированное покрытие.
24. Исторический forecast snapshot сохраняется и сравнивается с фактическими выплатами.
25. Поиск по wallet, referral link, Atlas ID и точному номеру личной ветки возвращает один и тот же канонический профиль участника.
26. Первая линия, структура, циклы и выплаты карточки воспроизводятся из ledger и referral graph на одном as-of block.
27. KPI-план хранит target, actual, срок и историю версий; изменение target не перезаписывает прошлое значение.
28. Просмотр полного адреса, операции с корпоративным финансированием и заметками отражаются в audit log.
29. Пользователь без `leader_management` не видит приватные заметки и документы финансирования.
30. Номера личных веток не перенумеровываются после сортировки, деактивации или исправления соседней записи.
31. Переход compression gap через предупредительный порог и через ноль создаёт один доказуемый сигнал на transition.

## Приложение B. Основные формулы

```text
Incoming Flow = Σ Confirmed Principal

Outgoing Flow = Σ Principal Returned
              + Σ Net Delta Received
              + Σ Net Partner Rewards Paid

Net Flow = Incoming Flow − Outgoing Flow

Accounting Liquidity(D) = Cumulative Incoming through D
                        − Cumulative Outgoing through D
                        + Approved Adjustments through D

Platform Fee Total = Platform Fee from Delta
                   + Platform Fee from Partner Rewards

Company Revenue = Platform Fee Total + Head Account Income

Company Revenue Rate = Company Revenue / Incoming Flow × 100%

Partner Reward / Incoming = Net Partner Rewards Paid / Incoming Flow × 100%

Cycle Inflow Share = Cycle Incoming Flow / Total Incoming Flow × 100%

Wallet to Cycle Conversion = Wallets with First Cycle / Connected Wallets × 100%

Liquidity Coverage Ratio = Available Accounting Liquidity /
                           Forecast Outgoing for Horizon
```
