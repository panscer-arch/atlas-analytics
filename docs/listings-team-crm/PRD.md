# SuperSUS Listings Team CRM v2

## Цель

Дать команде из 3–5 человек одну защищённую очередь для листингов и поиска партнёров, где сотрудники видят общую картину, но не выполняют одну работу дважды и не затирают изменения коллег.

## Принятые решения

- PostgreSQL — рабочее хранилище; прежний JSON используется только для одноразовой миграции и резервного восстановления.
- Каждая площадка хранится отдельной карточкой с `version`; изменения выполняются покарточно через `PATCH + If-Match`.
- Задача и карточка площадки — разные сущности. Одна площадка может последовательно иметь проверку, отправку, follow-up, проверку публикации и продление.
- «Взять задачу» — атомарная серверная операция. При одновременном клике первый сотрудник получает задачу, второй получает конфликт и имя владельца.
- Канонический домен и категория защищают от повторного создания площадки.
- Все мутации пишутся в неизменяемый журнал действий.
- Интерфейс обновляется каждые 15 секунд; WebSocket для команды такого размера не требуется.
- Старые просроченные задачи включаются в «Мой день», а не скрываются фильтром текущей даты.

## Рабочая модель

Активны три сотрудника с дневной ёмкостью 5 баллов каждый; два профиля находятся в резерве и включаются при росте команды. Командный минимум на день:

- 1 HYIP listing;
- 1 DApp listing;
- 1 бесплатная статья/PR;
- 1 MLM/direct-selling каталог;
- контакты LinkedIn, Facebook, Instagram и X;
- входящие ответы, просроченные follow-up, оплаты и проверки имеют приоритет над новым поиском.

Один сотрудник выбирает рабочий профиль, берёт свободную задачу, переводит её в работу и завершает либо возвращает в очередь. Система не позволяет двум людям одновременно закрепить одну задачу.

## MVP

- серверная миграция существующих карточек;
- 3 активных и 2 резервных участника;
- общая очередь и персональный «Мой день»;
- командная доска по сотрудникам;
- атомарный claim/release;
- версии карточек и задач;
- защита от дублей домена;
- идемпотентная генерация дневного плана;
- архив вместо физического удаления;
- аудит операций;
- polling 15 секунд;
- PostgreSQL production и сериализованный file fallback для локальной разработки/аварийного режима.

## Следующий этап

Персональная серверная авторизация (invite + отдельный пароль/Telegram identity), RBAC, согласования оплат, отдельное файловое хранилище пруфов, handoff с принятием, присутствие и уведомления. Выбор профиля в MVP обеспечивает рабочее разделение и аудит, но не является криптографическим подтверждением личности.

## Готовность

- два параллельных claim дают один успех и один `409`;
- устаревшая версия не перезаписывает свежую;
- повторная генерация плана не создаёт дубли;
- одинаковый домен в той же категории не создаётся второй раз;
- каждый успешный write создаёт audit event;
- существующие карточки не теряются при миграции;
- build, API regression, security review и browser smoke проходят до production deploy.
